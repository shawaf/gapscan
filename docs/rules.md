# GapScan Rules (own rule library)

GapScan ships its own Semgrep rules, licensed Apache-2.0 with the rest of the project, in
`packages/gapscan-security/src/gapscan/rules/semgrep/`. They always run, with or without the community rule folder, and
cover the languages the community rules barely reach and, because the packaged app does not ship the community
rules (their license forbids it), they are the app's whole Semgrep coverage.

Every rule carries a CWE, a confidence level and a fix-oriented message; the mobile rules also carry a MASVS tag. The server-side Kotlin rules live in the same folder and so carry one too: MASVS has no server controls, so they use the closest honest control (MASVS-CODE-4 for injection, MASVS-AUTH-1 for tokens, CORS and CSRF, MASVS-NETWORK-1 for cookie flags).

## Tests
Each rule has a vulnerable and a safe case in `tests/rules/<language>/`, written as Semgrep
`--test` annotations. `make rules-test` runs them; `tests/test_own_rules.py` runs them in the
suite and checks that every rule has its tags.

## How well they work (scanner only, no AI review)

### Method
`tools/rule_bench.py <language>` scores our rules next to the community rules on a labeled benchmark. A case counts as flagged when a finding in its file carries a CWE of the expected class (the OWASP scorecard rule), and the score is the true-positive rate minus the false-positive rate (Youden), per category and overall, the measure the published tool comparisons use.

To keep the numbers honest the cases are split in two halves by a hash of their name. **Rules are tuned looking at the dev half only; the test half is printed with `--final`, at checkpoints.** A rule may never mention a benchmark's own helper classes or names: it has to make sense in any application. Rules that came out of this work were each generalizations (provider arguments, letter case, request parameter *names* as a source, taint through collections, environment variables of a spawned process), not Benchmark tricks.

### Results by language (scanner only; our rules against the community Semgrep rules for the same language)
Score = catch rate minus false-alarm rate, in points. "Held-out" is the half of the cases that was never looked at while writing rules; it is printed with `--final`.

How to read it:
- **C# and PHP** are scored with `tools/lang_bench.py csharp|php [--final]` (C# and PHP rules were tuned on the dev half only; the test half was run once). Their sources are request data, the console, environment variables and sockets, not files or database values, so Juliet's `File` and `Database` variants and SARD's file/command/session inputs are misses by design (SARD: half its cases read their input from `/tmp/tainted.txt` through `fopen`, backticks or `exec`). The PHP suite also labels XSS by output context (an encoded value inside `<style>` or `<script>` counts as vulnerable), passes data through objects (constructor to getter, which a per-function rule cannot follow) and calls a few sanitizers safe that are not (HTML encoding before a shell command); we did not chase those labels. Known false alarm in C#: a value validated by parsing it as a number and then used in its original form.
- **Python (October 2026 round):** dev half +50 -> +63, held-out half +51 -> +58 (run once). The gains are sanitizers that real code uses: XPath quote escaping or rejection, URL host/scheme checks before a redirect, `..` rejection and resolve-then-`startswith`/`is_relative_to` containment, constant allow-list lookups, `fullmatch` validation, JSON (dict) responses; plus SQL built into a variable and `sh -c` lists. What remains is mostly the Benchmark's own tricks (constant-folded branches, list `pop` index shifts, dict keys read back), and two Semgrep limits: slicing a tainted string (`value[:50]`) drops taint, and a later clean `d[k] = ...` write clears taint from the whole dict. Python fixtures: recall 95% -> 100%, safe Python sites flagged 16/22 -> 12/22 (the safe fixtures were read while tuning).
- The community rules for Python, Kotlin and Swift cover very little of what these benchmarks test, so "better than the community rules" is a low bar there. A vendor-run comparison on the Java Benchmark (a competitor's page; read with care) reports Semgrep OSS +47.9, CodeQL +59.9 and their own engine +73.5, so on Java we are at the free-Semgrep level and below CodeQL, whose lead comes from following data across functions and files.
- **Real apps are much harder than the MASTG demos.** The demos are tidy samples built around one API each; in DIVA, InsecureBankv2, DVIA-v2 and iGoat-Swift the weakness is spread through view-controller code, storyboards and the manifest. Before the real-app rules were written we caught 0 to 7% of those files; now 30 to 50%. iOS (iGoat, 30%) remains the weakest ecosystem. The labels are mine, taken by hand from each app's challenge or exercise names, and only files with code that implements the weakness are labeled.
- **Server-side Kotlin has no benchmark yet.** The Ktor/Spring rules are checked only against their own test cases and the labeled fixtures (where they add a true positive and no false alarm); their catch and false-alarm rates on real servers are unknown. Semgrep's Kotlin taint is per function, so request data passed into a helper in another function or file is not followed.
- **Swift, October 2026 round.** 32 rules were added, tuned on the dev halves only. Each corpus's test half was run once at the end (MASTG 69%, DVIA-v2 50%, iGoat-Swift 30%). One slip: MASTG-DEMO-0096 (dev) is a symlink to the code of MASTG-DEMO-0095 (test), so that test-half file was read. No rule was written for it; the existing WebView file-access rule already covered it. Semgrep does not follow symlinks, so 0096 and 0143 (also symlinks) can never be flagged. Missing certificate pinning (MASTG-DEMO-0148) is not something a single file can show, so there is no rule for it. The Vapor rules carry MASVS-CODE-4, MASVS-AUTH-1 or MASVS-CRYPTO-2 only because every rule in the swift folder needs a MASVS control; there is no server-side Swift benchmark yet, so they are checked only by their test cases. `arc4random` and `Int.random` are not flagged: on Apple platforms both use the system's secure generator.
- **Dart is the weakest language and the least certain.** DVMA's modules are mostly behavioral simulations (intent routing, overlays, authorization) whose weakness is not visible to a static rule, and many module folders hold only a UI screen. Only the crypto, storage and network modules are realistically detectable. Treat 7% as a floor for what a rule can catch in such code, not as a measure of how well Flutter apps are covered.
- **Held-out discipline slipped on the mobile real-app sets.** I read some files of DVIA-v2, iGoat-Swift, KotlinGoat and DVMA from both halves, so those rows are labeled "tuned on all files" where that applies. DIVA/InsecureBankv2 (Android Java) is the cleanest held-out mobile row.
- The mobile corpora are tiny and almost all positives (the MASTG demos are mostly samples that fail a check), so they measure how much we catch but say little about false alarms. The JavaScript set is also small (82 cases); treat its numbers as an indication, not a precise score.
- The false-alarm rates of the pattern and taint rules are high on the Benchmarks (about 40% on Java), because their safe cases hide the fix in branches and collections. That is what the model review is for. Weak-random rules are low confidence (INFO) for the same reason.
- Fixtures regression check (128 labeled sites, own rules only): recall 97%, precision 66% (was 47% and 59% before the Python, JavaScript, Java and Go rules). The community rules plus ours score 91% / 62%.

## Limits
- Rules that name JDK classes use fully qualified names, so they match code with or without imports (this
  matters: the Benchmark writes `javax.crypto.Cipher.getInstance(...)` in full).
- Many rules are regular expressions over the source (the `generic` language), because Semgrep's
  Swift and Dart grammars cannot express every pattern. They are robust to formatting but they see
  text, not types, and some report the start of the function rather than the exact line (the
  weak-randomness rules say so in their message).
- Names decide "security-sensitive" (token, password, secret, ...), the same heuristic as the
  review step, so unusual names are missed.
- No data-flow: a rule cannot tell that an interpolated value was validated earlier. The model
  review and the flow trace handle that.

Add a rule by editing the YAML, adding a vulnerable and a safe case with `// ruleid:` and
`// ok:` annotations, and running `make rules-test`.
